# 아베오 비공개 서버 저장 초안

현재 상태: 로컬 구현·검증 완료, 외부 계정/프로젝트/권한 생성·커밋·게시 미실행. `cloud-config.mjs`는 disabled이며 공개 운영 사이트는 기존 로컬 저장판을 유지합니다.

## 서비스와 저장 위치

제안은 별도 **Supabase 프로젝트 `car-care-aveo`의 PostgreSQL + Supabase Auth**입니다. GitHub Pages는 앱 정적 자산만 제공하고 차량 데이터는 서버의 계정별 문서/변경 이력에 저장합니다. 일반 Drive/Sheet 파일은 방문자의 계정을 확인하고 쓰기를 안전하게 제한하는 서버가 아니므로 만들지 않았습니다.

Supabase 프로젝트의 관리자와 실제 후배 계정은 아직 선정·확인되지 않았습니다. 대학 운영 프로젝트·계정·OAuth와 연결하지 않습니다. 프로젝트 지역 및 요금제는 승인할 때 확정하며, 무료 사용 또는 지속 운영을 보장하지 않습니다.

## 접근 통제

- 로그인은 이메일·비밀번호 방식의 **승인된 기존 계정**을 사용하도록 구현했습니다. 앱 자체에 회원가입·OAuth 연결·사용자 초대 기능은 없습니다. 실제 계정 등록/초대·확인은 승인 후 관리자 또는 사용자가 수행합니다.
- 세션은 메모리에만 유지하며 새로고침 후 다시 로그인합니다. 앱은 비밀번호·토큰을 localStorage에 보관하지 않습니다.
- `car_care_private.members`에 관리자가 확인한 auth user id만 등록합니다. 로그인 성공만으로 읽기/쓰기 권한을 받지 않습니다.
- RLS는 본인 문서와 본인 변경 이력 조회만 허용합니다. 익명 조회 및 직접 insert/update/delete는 차단합니다.
- 쓰기는 권한과 `auth.uid()`를 검사하는 RPC만 허용합니다. 다른 사용자의 id를 전달하는 API 자체가 없습니다. SECURITY DEFINER 함수의 search_path를 고정하고 공개 실행 권한을 제거했습니다.
- 프런트에는 publishable key만 허용합니다. secret/service_role/관리 토큰은 넣지 않습니다. 승인된 프로젝트 origin만 빌드 결과 CSP `connect-src`에 넣고 기본값은 `'none'`입니다.

## 동기화와 복구

- 계정 로그인은 서버 기록 조회만 수행합니다. 로컬 원본은 KEY `car-care-log:v1` 그대로 보존합니다. 최초 기록이 없으면 ‘기존 기록 이관 검토’ 또는 ‘새 서버 기록 시작’을 선택하고 계정·내용 확인 후 저장합니다.
- 로그인 상태에서는 서버 저장 응답 성공 후에만 화면의 확정 기록을 바꿉니다. 계정별 데이터는 브라우저 원본 키에 저장하지 않습니다. 로그아웃하면 원래 로컬 기록으로 돌아옵니다.
- 모든 쓰기는 예상 revision과 mutation UUID를 사용합니다. 오래된 화면의 덮어쓰기는 거부하고 동일 요청 재시도는 중복 변경 이력을 만들지 않습니다. 네트워크 결과가 불확실하면 같은 입력의 재시도로 확인하며 다른 입력을 바로 덮어쓰지 않습니다.
- 실패한 저장은 폼과 입력을 유지하며 완료로 표시하지 않습니다. 임의 자동 충돌 병합이나 오프라인 쓰기 큐는 없습니다. 서버 최신 기록 확인은 사용자가 명시적으로 수행합니다.
- 변경마다 전체 스냅샷을 저장합니다. 최근 50개 이력을 표시하고 선택 버전 복구 시 새 revision을 추가합니다. 원래 버전도 유지합니다. 저장량은 이력 크기와 함께 증가하므로 실제 운영 전에 보관기간/용량 정책을 정해야 합니다.
- 변경 이력과 동기화는 프로젝트·계정 삭제나 서버 장애에 대한 별도 백업을 보장하지 않습니다. 운영자는 별도 암호화 백업 위치·보관기간·복구 시험을 결정해야 합니다. JSON/CSV 기능은 보조 수단으로 유지합니다.

## 검증

`npm ci --ignore-scripts && npm run build:cloud && npm run stage:pages && npm test`

- 49/49 통과: 기존 30개 + cloud/설정 8개 + UI 3개 + 실제 PostgreSQL 엔진(PGlite) SQL/RLS 5개 + 차량 정보/기존 백업 호환 3개.
- SQL 권한·회원 분리·익명 차단·직접 쓰기 차단·revision 충돌·idempotency·복구 이력·서버 스키마 검증 확인.
- UI 테스트는 mock Auth/RPC를 사용합니다. hosted Supabase의 실제 인증, 이메일 발송, 다중 연결 동시 실행, 모바일 실제 로그인은 미검증입니다. PGlite는 단일 연결이며 운영 DB의 동시 트랜잭션 시험을 대체하지 않습니다.

## 필요한 정확한 승인과 후속 실행

1. 전용 Supabase 프로젝트 사용/생성, 관리자 계정, 지역·요금제 승인. 새 계정의 약관 동의는 사용자가 직접 수행합니다.
2. 이메일·비밀번호 인증 운영 설정과 **실제 확인한 후배 auth user**의 등록·members 허용 승인. 임의 이메일/공개 공유/새 OAuth는 사용하지 않습니다.
3. 전용 프로젝트에 `schema.sql`을 설치하는 비공개 데이터베이스/함수/권한 설정 승인. 실제 JWT A/B/익명, 첫 이관 경쟁, 재시도·충돌, 복구를 staging에서 확인합니다.
4. 프로젝트 URL·publishable key를 설정하고 CSP origin 및 정적 번들 배포 변경 승인. 프런트 데이터 전송 목적지는 이 전용 프로젝트 한 곳입니다.
5. 운영자의 별도 백업 위치·보관 정책·비용/무료 한도 확인. 필요한 새 지속 자격증명이나 접근 권한은 구체 승인을 받습니다.
6. 이번 로컬 패치 Git 커밋 범위 승인 여부를 먼저 보고한 뒤 커밋/PR. main workflow가 자동 배포하므로 운영 배포 승인 전 merge는 하지 않습니다.

근거: [이메일 로그인](https://supabase.com/docs/guides/auth/passwords), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [함수 권한](https://supabase.com/docs/guides/database/functions), [백업](https://supabase.com/docs/guides/platform/backups). 공식 문서는 무료 요금제의 별도 외부 export를 권고하며 유료 요금제의 백업 정책은 별도로 설명합니다.

## 차량 정보와 추후 읽기 전용 연결

차종·연식·엔진/배기량·연료·변속기·주행 환경을 별도 입력합니다. 버전 1 백업은 원본을 건드리지 않고 버전 2 구조로 읽으며 새 정보를 추정하지 않습니다. 충분한 정보가 있어도 현재 확보한 공통표의 특정 연식 적용은 미확인이므로 확정 주기를 자동 선택하지 않습니다. 수동/자동/CVT/DCT에 맞지 않는 공통 변속기 참고 행은 제외합니다. 개별 연식 취급설명서 근거를 확보한 이후 검증한 profile을 추가해야 합니다.

담곰 등의 향후 연결은 `car_care_read/history/version` 읽기 API를 재사용할 수 있는 구조입니다. AI 공급자 키·과금·자동 전송·연결 권한은 만들지 않았습니다. 실제 연동 전에는 사용자의 데이터 전송 승인과 별도의 읽기 전용 도구 권한을 설계해야 하며 현재 앱의 쓰기 가능한 세션/관리 토큰을 봇에 전달하지 않습니다.
